# Подбор скилов под задачу

Скил под задачу ищется **до** начала работы, а не когда стало тяжело. Порядок жёсткий:
сначала посмотреть, что уже стоит; потом поискать готовое; и только потом писать своё.

## Шаг 1. Что уже есть

```bash
ls ~/.claude/skills/ .claude/skills/ 2>/dev/null | sort -u
```

Сопоставь задачу с установленным. Названия обманчивы — «фронтенд-скил» на самом деле
`frontend-agent`, «бэкенд-скил» — `backend-engineering`. Сверяйся с таблицей имён
в `required-skills.md`.

Нашёл подходящий — **объяви его вслух** и следуй ему:

> Беру `backend-data-persistence` — он про схемы базы и миграции, ровно наша задача.

Если ученик только начинает и у него не стоит ничего — не подбирай поштучно,
дай стартовый набор: `references/recommended-stack.md`.

## Шаг 2. Поиск готового

Если ничего не подошло — ищем в экосистеме, не изобретаем:

```bash
npx skills find "<ключевые слова задачи>"
```

Перед тем как ставить, проверь три вещи. Порядок важен:

1. **Установки.** Больше 1000 — можно доверять. Меньше 100 — скепсис.
2. **Автор.** `anthropics`, `vercel-labs`, `microsoft`, `obra` — надёжны. Незнакомый автор
   с 5 установками — читай исходник целиком перед установкой.
3. **Что внутри.** Скил выполняется с полными правами агента. Открой `SKILL.md` глазами.

Установка:

```bash
npx skills add <owner>/<repo>@<skill> -g -y
```

Ученику скажи, что ставишь и зачем — одной строкой, без списка альтернатив.

**Важно:** индекс `npx skills find` бывает устаревшим. Если установка падает с
«No matching skills found», склонируй репозиторий и посмотри реальные имена папок —
скил могли переименовать.

## Шаг 3. Когда писать свой

Пиши свой скил, только если выполнены **все три** условия:

- Поиск не дал ничего пригодного
- Приём понадобится **снова** — в этом проекте или в следующем
- Его нельзя заменить строчкой в `CLAUDE.md` проекта

Не пиши скил для одноразового решения, для того что уже есть в документации,
и для проектных договорённостей — последним место в `CLAUDE.md`.

Пишешь — бери `writing-skills` (или `skill-builder`) и следуй его методике:
описание только с триггерами, тяжёлое в `references/`, таблица рационализаций.

**Честно предупреди ученика:** скил, написанный и не прогнанный через проверку,
может оказаться дырявым. Это черновик, а не инструмент.

## Как часто это уместно

Раз в задачу — нормально. Три новых скила за сессию — признак, что ты уходишь
от работы в обустройство рабочего места. Ученик пришёл строить проект,
а не собирать инструментарий.

Ставь ровно то, что нужно текущему шагу.

## Что говорить ученику

Коротко и через пользу, без внутренней кухни:

> 🟢 **ХОРОШО ПОЛУЧАЕТСЯ**
> Задача про миграции базы — на это есть готовый скил `backend-data-persistence`.
> Беру его, он держит в голове порядок операций, который легко забыть.

Если пришлось написать свой:

> Готового не нашлось — набросал свой скил на этот приём.
> Это черновик: он не проверен, и если начнёт мешать, скажи, поправим.
